Dark mode, from the first paint.

Follow the device by default. Let people choose Light, Dark, or System in Settings → Appearance. Keep that choice after a reload.

Status: proposed implementation. This page follows your device theme. The app has not been changed.

01 · What people get

System · default

Match the device theme, including changes while the app is open.

Light

Keep the light theme even when the device uses dark mode.

Dark

Keep the dark theme even when the device uses light mode.

  • Add Appearance after General. General stays the default tab. Support ?settings=appearance.
  • Use a labeled native radio group with Light, Dark, and System. Changes apply at once; no Save button. System has the hint “Match your device settings.”
  • Save a raw string under mado:theme in localStorage. The choice belongs to this browser and site, across guest and signed-in accounts.
  • Missing or invalid values mean System. If storage is blocked, changes still work for this page session. A reload falls back to System.
  • Other open tabs follow saved changes. Removing the key or clearing storage returns them to System.
  • Set the theme before content paints. Theme changes are instant; add no page-wide color animation.
  • Keep images, videos, and website embeds unchanged. External embeds may keep their own theme.

Why three options? A switch cannot express both a fixed choice and “follow the device.” Browser-wide storage also lets the startup script read the choice before account loading.

04 · Data and control flow

Data flow

localStorage: mado:theme + device prefers-color-scheme
  → preference (light | dark | system)
  → resolved theme (light | dark)
  → html.dark + CSS color-scheme
  → shared tokens → app, portals, native controls, toasts

radio choice → store setter → in-memory snapshot + localStorage
  → subscribers → selected radio + root theme

Control flow

  1. The server renders a stable shell without reading browser APIs.
  2. The head script reads the saved choice safely, resolves System, and sets the root class before content paints.
  3. After hydration, the root subscriber starts the store, reads the latest browser state, and attaches storage and device listeners. Re-read after attaching to close the startup gap.
  4. A user choice updates memory and the DOM immediately. Try saving; a storage failure keeps the in-memory choice.
  5. A device event changes the DOM only under System. A matching storage event replaces the preference and updates subscribers.
  6. The last unsubscribe removes listeners. Setup must remain safe under repeated mounts.

Domain boundary: theme is a synchronous browser preference owned by settings. It needs no React Query, auth, IndexedDB, OPFS, or API calls.

05 · Function and component sketch

These are behavior sketches, not code ready to paste.

createSettingsThemeStore and its private helpers 
createSettingsThemeStore(browser):
  keep one cached snapshot; keep a listener set
  getSnapshot(): return cached snapshot
  getServerSnapshot(): return shared SYSTEM_LIGHT snapshot
  subscribe(listener):
    add listener; on first subscription attach browser events
    refresh from storage and device after attaching
    on cleanup remove listener; if none remain detach events
  setPreference(choice):
    validate choice; keep it in memory
    applyTheme(resolveTheme(choice, device))
    try localStorage.setItem(KEY, choice)
    publish only if preference or resolved theme changed
  onDeviceChange(): refresh resolved theme from in-memory choice
  onStorage(event):
    if localStorage and key is KEY or null:
      read saved choice; resolve, apply, publish
  return stable getSnapshot, getServerSnapshot, subscribe, setPreference

parseThemePreference(raw):
  return raw if light, dark, or system; otherwise system

readThemePreference(storage):
  try return parseThemePreference(storage.getItem(KEY))
  catch return system

resolveTheme(preference, deviceIsDark):
  if preference is system: return dark if deviceIsDark else light
  return preference

applyTheme(resolved):
  toggle document.documentElement.classList dark by resolved
  CSS on html / html.dark supplies color-scheme
useSettingsTheme, SettingsThemeSync, SettingsAppearanceTab 
useSettingsTheme():
  lazily get the one browser store; never share mutable state on server
  snapshot = useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot)
  return snapshot and stable setPreference

SettingsThemeSync():
  useSettingsTheme()
  return null

SettingsAppearanceTab():
  { preference, setPreference } = useSettingsTheme()
  render fieldset with legend “Theme”
  render Light, Dark, System native radios with shared name
  checked follows preference; onChange calls setPreference
  render “Match your device settings.” hint for System
getSettingsThemeBootstrapScript 
getSettingsThemeBootstrapScript():
  return static self-contained script using shared key and pure rules:
    preference = safely read storage, default system
    deviceIsDark = matchMedia('(prefers-color-scheme: dark)').matches
    resolved = resolveTheme(preference, deviceIsDark)
    toggle html.dark

RootDocument integration:
  html: suppress expected root attribute hydration warning only
  head: static bootstrap script, then HeadContent
  body: SettingsThemeSync, existing children, Toaster, Scripts

Test the emitted script and runtime with one input matrix so their rules cannot silently drift. Inspect the rendered HTML to confirm script order. The server snapshot keeps the radio markup stable during hydration; the browser snapshot then selects the saved choice.
