Desktop library folder

In the desktop app, the library is a folder the user picks. It holds the files and the records as plain files, so Finder shows them and an AI agent (Claude Code, Codex) can read and edit them.

Goal Pros and cons Folder layout What we add What we reuse Web vs desktop Data flow Control flow Pseudo code Verify Risks Build order

1. Goal and decisions

  • Desktop only. The web app keeps IndexedDB and OPFS, and its behavior does not change.
  • The user picks the folder. The UI calls it the Library folder. It is shown in Settings → Data → Storage and can be changed there.
  • No browser storage on desktop. The storage quota is hidden on desktop, because the browser's number says nothing about a folder on disk.
  • One small JSON file per source. This is the change from v1 of this plan. An agent opens one small file, edits tags, and saves it. The app notices and reloads it.
  • Files are the truth, memory is the index. The app reads the folder at start and keeps the records in memory for fast search. A disposable cache can come later.
  • No sync yet. Desktop and web are separate libraries until there is a backend. A web user moves over with Export, then Import.
  • Out of scope for now: the CLI runner, the API, the canvas file, moving a library to a new folder, and a lock file.

2. Pros and cons

Pros

  • The user sees and owns the files in Finder.
  • An agent can read and edit one small record. No SQL, no locked database file, and a clean diff.
  • Time Machine, iCloud Drive or Dropbox can back the folder up with no work from us.
  • No browser quota, and the browser can't clear the data.
  • The folder survives deleting the app, and moves to another Mac.
  • One small file is rewritten per change, so it scales better than one big file.
  • The web app is unchanged.
  • The LibraryStore seam is where sync plugs in later.

Cons

  • A real refactor: raw IndexedDB calls in three files move behind a store. A careless change can break the web app.
  • Two storage paths to test and keep working.
  • Many small files, so the first scan at start is slower than reading one file. A cache fixes this later.
  • No transactions. Deleting a collection touches many files, and a crash can leave it half done.
  • An agent can write bad JSON or edit while the user edits. The app must validate, and a rule must pick the winner.
  • Big videos can't be copied over IPC in one piece. We write in chunks and read through a custom protocol.
  • A folder in iCloud or Dropbox can evict files or make conflict copies, and two Macs on one folder will clash.
  • macOS asks permission for Desktop, Documents and external drives. An unplugged drive means a missing folder.
  • Files in media/ have random names, so Finder is not yet nice to browse.

Options for storing the records

Option Pros Cons Pick?
A. One library.json Simplest. Close to the export file. Rewrites everything on each change. Hard for an agent at a large size. No
A2. One JSON file per source Small writes. An agent edits one file. Readable. No native module. Many files. Needs a startup scan, a watcher and validation. Yes
B. SQLite in the folder Fastest at any size. Real queries. Native module to build and sign. Binary file, awkward and risky for an agent. No. Maybe as a disposable cache
C. IndexedDB cache, folder as truth No rewrite of the feature queries. Two copies to keep in step. More bugs. No

3. Folder layout

<folder the user picked>/Mado Library/
├── AGENTS.md           rules for an AI agent: the schema and what it may change
├── collections.json    every collection, with its parent
├── sources/
│   ├── 5f0c…a1.json    one source: name, note, tags, collections, sizes…
│   └── 9b21…e7.json
└── media/
    ├── 5f0c…a1         the file, named by its storageKey
    └── 9b21…e7
  • A source's JSON is the same shape the app already uses (the Source type), so a text body and a website preview stay inside the record.
  • The record names its file by storageKey, not by a full path. Moving or renaming the folder breaks nothing.
  • The pointer to the folder is in ~/Library/Application Support/Mado/config.json. It holds only the folder path.
  • Later: projects/<id>/canvas.json for each canvas. Tldraw and Excalidraw files are plain JSON, so an agent can edit them. (Pen's own .pen files are encrypted, so they are not a model for this.)

5. What we reuse

  • writeMediaFile, readMediaFile and deleteMediaFile in source-media.ts. They are already a small seam.
  • The existing action tests (source-actions, collection-actions, import-actions, export-actions). They run on IndexedDB and prove the refactor changed nothing on the web.
  • The Source and Collection shapes. No new data model.
  • Import and Export, as the way to move a web library into the desktop app.
  • mediabunny compression, which keeps running in the renderer.
  • The Electron shell on this branch (apps/desktop).

6. Separating web and desktop

apps/web       all UI and features. The only place UI lives.
apps/desktop   Electron main + preload only. No UI.
  1. Interfaces for anything platform-specific. LibraryStore and the media functions have a web version and a desktop version. Later: AgentRunner and FolderPicker.
  2. One place decides the platform. getDesktopBridge() returns the bridge or undefined. Feature code asks for a capability, and never checks "isDesktop" on its own.
  3. Desktop-only UI hides by capability. The folder gate, the Library folder row and the live reload render only when the bridge exists.
  4. Dependency rule. apps/web never imports from apps/desktop. The desktop holds no UI. The bridge type lives in the web app, and the desktop implements it.

8. Control flow

First run

  1. The gate asks the bridge for the Library folder. There is none.
  2. It shows "Choose where to keep your library".
  3. The user picks a folder. Main creates Mado Library/, writes AGENTS.md and saves the path.
  4. Main loads the (empty) library and starts the watcher. The app opens.

Add a source

  1. The renderer compresses the file, as it does today.
  2. It writes the bytes to media/<storageKey> in chunks. The file appears only when complete.
  3. Only then does it save the record, so a failure leaves no half record.

An agent edits a record

  1. The agent changes tags in sources/<id>.json.
  2. The watcher sees the change and waits a moment for the write to finish.
  3. If the new text equals what the app last wrote, it is the app's own write. Ignore it.
  4. If it is valid, update the index and tell the renderer. If it is not valid, keep the last good record and log the problem.

Next start

  1. Main reads the saved path and checks the folder exists.
  2. It reads collections.json and every file in sources/. A broken file is skipped and logged, never fatal.

The folder is missing (drive unplugged, folder renamed)

  1. The app does not create a new empty library by itself.
  2. The gate shows "We can't find your library" with "Choose folder".

Change folder (Settings)

  1. The user picks another folder.
  2. The app opens the library there, or creates one. It does not move or copy files, and tells the user the old files stay where they are.

9. Pseudo code

LibraryStore (the contract) 
interface LibraryStore
  listCollections() -> Collection[]
  getCollection(id) -> Collection | undefined
  putCollections(collections)
  deleteCollections(ids)
  listSources() -> Source[]                  // trash included
  getSource(id) -> Source | undefined
  listSourcesInCollection(collectionId) -> Source[]
  addSource(source)                          // fails if the id exists (import needs this)
  putSources(sources)
  deleteSources(ids)

These are the only operations the three feature files use today.

getDesktopBridge() and getLibraryStore() (renderer) 
function getDesktopBridge()
  // The bridge exists only inside the Electron window.
  return window.madoDesktop   // undefined on the web

function getLibraryStore()
  bridge = getDesktopBridge()
  return bridge ? desktopStore(bridge) : indexedDbStore
chooseLibraryFolder() (main) 
async function chooseLibraryFolder()
  picked = await dialog.showOpenDialog({ properties: [openDirectory, createDirectory] })
  if picked.canceled
    return null
  root = join(picked.filePaths[0], "Mado Library")
  create root/sources and root/media
  write root/AGENTS.md if missing
  // A path in a config file survives restarts with no permission prompt.
  writeConfig({ libraryRoot: root })
  return root
openLibrary(root) and writes (main) 
function openLibrary(root)
  collections = readJson(root/collections.json) or []
  sources = new Map()
  for file in list(root/sources/*.json)
    try
      record = parse(read(file))
      if isValidSource(record, file) then sources.set(record.id, record)
      else log("skipped", file)
    catch log("skipped", file)
  return { collections, sources }

async function writeSource(root, source)
  text = stringify(source, indent 2)
  remember(source.id, text)                  // lets the watcher ignore our own write
  writeAtomic(root/sources/id.json, text)    // temp file, then rename

async function putSources(sources)
  for source in sources
    index.set(source.id, source)             // never mutate the old object
    await writeSource(root, source)

async function deleteSources(ids)
  for id in ids
    index.delete(id)
    unlink(root/sources/id.json), ignoring "not found"
watchLibrary(root, onChange) (main) 
function watchLibrary(root, onChange)
  watch(root, recursive, event =>
    debounce 150 ms per file, then
      if file is sources/*.json
        text = read(file) or null              // null: the file was deleted
        if text equals remembered(id)  return  // our own write
        if text is null
          index.delete(id)
        else
          record = tryParse(text)
          if not isValidSource(record, file)
            return log("bad edit, kept the last good record", file)
          index.set(id, record)
        onChange({ kind: "sources" })
      if file is collections.json
        reload collections, onChange({ kind: "collections" }))
Media write, read and remove (main) 
async function beginWrite(key)             -> handle with an open temp file
async function appendChunk(handle, bytes)  // 8 MB at a time, so IPC memory stays small
async function finishWrite(handle)
  close(temp)
  rename(temp, media/key)                  // the file appears only when complete

async function removeMedia(key)
  try unlink(media/key) catch NotFound -> ignore

function registerMediaProtocol()
  protocol.handle("mado-media", request =>
    key = parseKey(request.url)            // only letters, digits and "-"
    return net.fetch(pathToFileURL(media/key))   // range requests work, so video seeks)

11. Risks and open questions

  • Refactor size. source-actions.ts has many call sites. We change them in small steps, and the tests run after each.
  • Read then write across IPC is not one transaction. IndexedDB gave us that. With one user it is fine. If a race shows up, add an updateSource(id, fn) that runs in the main process.
  • User and agent edit the same record. v1 rule: the file on disk wins, and the renderer reloads. Revisit when the CLI runner exists. It may need an "AI is editing" state.
  • Accounts. The web keeps one database per account. The desktop library is one per folder, so it ignores the signed-in account for now. Revisit with sync.
  • Folder in iCloud, Dropbox or a network drive. Warn later, and add a lock file so two instances do not write together.
  • Large reads in the renderer. readMediaFile loads a whole file as a Blob. Fine for images, heavy for a 1 GB video. A direct mado-media:// URL for the player is the next step.
  • Readable names in Finder. A mirrored view like the export layout is a later phase.
  • Export on desktop uses the browser save picker. Check that it works in Electron.

  1. Baseline. Run the web tests. (Done: 455 pass, 1 unrelated failure in landing-motion.)
  2. Records in the main process. library-records, library-folder and their tests.
  3. Media in the main process. library-media and the protocol.
  4. Bridge. IPC, preload and window safety.
  5. Web seam. LibraryStore, the IndexedDB store (tests still green), then the desktop store.
  6. Move the three feature files onto the store, then the media functions.
  7. UI. Folder gate, Library folder row, hidden quota, live reload.
  8. Watcher. Agent edits reload the app.
  9. Docs. desktop.spec.md, a row in AGENTS.md, storage.spec.md, settings.spec.md, ARCHITECTURE.md and the roadmap, in the same commits as the behavior.

Later, not in this round: the canvas file, the CLI runner, moving a library, a lock file, and a disposable index cache.
