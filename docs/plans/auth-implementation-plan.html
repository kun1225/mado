01 · Decisions and scope

Express + Better AuthKeep apps/api. Let Better Auth handle authentication.
PostgreSQL + DrizzleStore users, accounts, sessions, and verification records in your own database.
Cookie sessionsUse database sessions. Skip custom JWT logic and Redis for the first version.

Include email/password sign-up, email verification, sign-in, sign-out, password reset, and protected pages/API routes. Leave social login, passkeys, organizations, and roles for later.

Assumptions: “No third-party service” means no hosted auth provider. Open-source packages are allowed. Use your own SMTP server if all services must be self-hosted. Production will serve the web app and /api under one origin.

Data boundary: Existing collections and sources use browser storage. Login does not make them private or sync them. Before release, choose how local data belongs to accounts. Do not silently upload it, delete it, or expose one account’s local content to another. Backend data sync is a separate feature.

02 · Backend structure: routes, controllers, models

Group backend code by domain. Keep related request handlers together in one controller file. Only extract another file when it has a clear purpose. This structure does not require putting every helper into a controller: configuration, database access, and frontend code keep their own roles.

Request → route → controller → model/database → response

Better Auth exception: /api/auth/* goes from auth.route.ts directly to Better Auth’s handler. Better Auth already provides the controllers for sign-up, sign-in, verification, and password reset. Do not wrap each endpoint in a duplicate controller or reimplement its database logic.

Custom endpoints: keep their request logic in auth.controller.ts. Use models for database tables and queries. Keep shared database setup outside the auth domain.

03 · Data flow

Form → Better Auth client → /api/auth/* → Express Better Auth handler → Drizzle → PostgreSQL
Response → HttpOnly session cookie → browser
Later request + cookie → session lookup → allowed user data or 401

Email flow: Better Auth creates a short-lived token → sendAuthEmail → SMTP → user opens link → Better Auth checks token → verifies email or resets password.

SSR flow: protected route → request-scoped server function → forward Cookie header to the fixed API origin → read session → render page or redirect. Forwarding the browser’s cookie is required during server rendering.

04 · Control flow

  1. Sign-up: validate input → create account → send verification email → show “check your inbox.” No session until verification succeeds.
  2. Verification: Better Auth checks link → show result → user signs in. Expired links offer resend.
  3. Sign-in: check credentials and verified email → create session → set cookie → navigate to the validated local return path or /library.
  4. Protected request: check session on the server → allow or return 401. A page redirect does not protect an API.
  5. Password reset: always show a neutral request result → check reset token → set new password → revoke existing sessions → ask the user to sign in.
  6. Sign-out: revoke session → clear account query data → return to sign-in. Local storage follows the explicit ownership policy.

Validate redirect targets as local paths; reject external URLs and protocol-relative URLs. Show a retry state for server/network errors. Preserve entered form values when safe; never preserve passwords outside the form.

06 · Delivery order

  1. Foundation: add PostgreSQL, Drizzle, Better Auth, its matching adapter, and SMTP support. Add environment validation and .env.example. Generate and review auth migrations.
  2. Backend: wire auth into createApp; configure trusted origins, cookie security, verification, reset mail, session expiry, and login/reset rate limits. Keep health public; decide whether site previews require login before attaching the guard.
  3. Frontend: add forms, routes, SSR-aware session checks, protected route guards, and sign-out.
  4. Release: finish the local-data ownership policy; run integration checks, test email links, apply migrations, and verify HTTPS cookies on the production origin.

Checks that matter

  • Fresh database migrations succeed; normal app startup does not run migrations automatically.
  • New account cannot sign in before verification; valid verification allows login.
  • Wrong passwords fail; duplicate sign-up and reset requests avoid account disclosure.
  • Anonymous protected API requests return 401; authenticated requests succeed.
  • Protected pages redirect correctly both on direct SSR visits and browser navigation.
  • Sign-out invalidates the session; expired sessions cannot access private routes.
  • Reset links expire and cannot be reused; password reset revokes old sessions.
  • Untrusted origins and external return paths are rejected; rate limits apply.
  • Mail failure has a recoverable resend path; SMTP credentials and auth secrets stay server-only.

Configuration: DATABASE_URL, BETTER_AUTH_SECRET, BETTER_AUTH_URL, WEB_ORIGIN, SMTP host/port/credentials, and mail sender. Validate required values at startup. Keep secrets out of source control and browser builds.

Done means: the full sign-up → verify → sign-in → protected page → sign-out flow works, password recovery works, server checks pass, and switching accounts cannot reveal another account’s local content.
